# 高风险操作双人复核（审批状态机）设计

- 日期：2026-10-07
- 状态：待评审（D1~D10）
- 归属：能力全景表 §3.6 行 186「高风险操作双人复核」（P2 / M，2026-10-05 明确为**保留项**）
- 前置结论：**不放开任意执行**，只给既有**参数化动作**加一道人审

---

## 1. 起因与依据

能力全景表 §3.6 行 186：

> 高风险操作双人复核 | 未实现（**保留项**）| `README.md` 路线图 P2。防的是误操作与单人误判，**不需要会话代理**，
> 也不需要完整工单引擎——一小块审批状态机即可（工单/审批流引擎是 3.6 的另一件大事，别混在一起）。
> 2026-10-05 明确为**保留项** | P2 | M | 审批状态机 + 权限（**不必**等工单引擎）

三条既有依据：

1. **它是"放开任意执行"的前置条件之一**（§3.4 后「操作面安全边界」第 4 条）：
   "若将来确实要放开任意执行，前置条件是**双人复核 + 不可篡改审计**，而这两条现在都不具备"。
   ——**但本批不放开任意执行**（见 §4 D9），因此可以单独做。
2. **验证矩阵里早有这条用例**：`docs/testing/2026-10-05-platform-validation-matrix.md:62`（用例 7-07）
   "双人复核 N：**申请人不可批准本人任务，超时自动失效，审计记录审批链**"——
   本设计的三条决定性判据直接取自它。
3. 同文件 `:192` 的结论："接已有参数化处置任务和审批状态机（双人复核），**不先上大型通用工单引擎**"。

**缺口**：现在任何一个持 `ops:exec` 的账号，点一下就把动作下发到远端（`ops_api.go:190` 直接 `a.ops.Create`）；
唯一的"把关"是前端各页自己写的 `ElMessageBox.confirm`（如 `OpsView.vue:740`）——
那是**同一个人再点一次**，防不了误判，更防不了单账号被盗。

## 3. 设计

### 3.1 实体与状态机

新增**审批单（approval request）**，与 ops 任务**并列**而不是嵌进它：

```
pending ──approve──► approved ──(立即执行)──► executed
   │                    │
   ├──reject──► rejected └──执行失败──► failed（动作本身失败，审批已通过）
   ├──cancel──► cancelled（仅申请人）
   └──超时────► expired
```

- 审批单**自带完整动作**（`kind` + `params` + `node`），因此批准后能**自动执行**，
  不需要申请人再点一次（否则"批了但没人执行"会变成新的糊涂账）。
- 执行时创建 ops 任务，`Operator` 记为**申请人**（谁想做这件事），审批链另存——
  这样 ops 任务页看到的仍是"谁要做的"，而审计能回答"谁批的"。

### 3.2 拦截点与"要不要审批"的判定

统一收口到一个函数（**唯一判定处**，避免各 handler 各写一遍）：

```go
// needsApproval 判定这次动作是否需要人审。
func (a *API) needsApproval(kind string) bool
```

- 调用点：`handleOpsCreate`（`ops_api.go:190` 之前）、`handleOpsCreateBatch`、
  `handleDefenseAction`、系统升级 apply/rollback、Agent 升级。
- 需要审批时**不创建任务**，而是创建审批单，返回 **202** + `{approvalId, state:"pending"}`。
- 前端据此提示"已提交审批，等待他人批准"，而不是"已下发"（**这条文案差别是本批最容易被忽略的正确性**：
  把"进了审批"说成"已下发"，操作者会以为指令已经跑了）。

### 3.3 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/v1/approvals?box=pending\|mine&state=&limit=` | `approval:read` | `pending`=待我审批（排除我自己提交的）；`mine`=我提交的 |
| GET | `/api/v1/approvals/{id}` | `approval:read` | 详情（含动作参数与审批链） |
| POST | `/api/v1/approvals/{id}/approve` | `approval:approve` | 批准并立即执行 |
| POST | `/api/v1/approvals/{id}/reject` | `approval:approve` | 驳回（必填理由） |
| POST | `/api/v1/approvals/{id}/cancel` | `approval:read` | 撤回（**仅申请人本人**） |
| GET/PUT | `/api/v1/approvals/config` | `approval:read` / `approval:manage` | 开关与范围 |

### 3.4 权限与内置角色

新增权限域「审批」：`approval:read`（看）、`approval:approve`（批）、`approval:manage`（改配置）。

- **批准需要两个条件同时满足**：持有 `approval:approve` **且**持有该动作本身所需的权限点
  （例如批准一次 `svc.restart` 需要 `approval:approve` + `ops:exec`）。
  理由：否则一个"只会点批准"的角色可以批准它自己都做不到的事，审批就退化成了橡皮图章。
- 内置角色：**运维管理员**、**安全管理员**、**超级管理员**给 `read + approve`；
  `approval:manage` 只给超管；只读用户/告警管理员不给。
- `approval:*` **不进** `HighRiskPermissions`（审批本身不是远端动作）。

### 3.5 资源范围

**申请人与审批人都必须在目标节点的范围内**（复用 `filterByNodeScope`）：
- 申请人越界 → 与今天一致（404/403）；
- 审批人越界 → 该审批单**不出现在他的待办里**，直接调 approve 也拒绝。
理由同合规矩阵那条："看得见才批得动"；导出/审批都是最容易漏范围的地方。

### 3.6 审计（审批链）

每次流转一条，`Category: "approval"`：

| Action | Detail 要点 |
|---|---|
| `create:<kind>` | 申请人、节点、动作、参数摘要、审批单号 |
| `approve` / `reject` | 审批人、审批单号、理由 |
| `cancel` / `expire` | 谁撤的 / 超时失效 |
| `executed` | 审批单号 → ops 任务号（把两段接起来） |

`Detail` 里**不回显文件内容**（`file.push` 只记 sha256 与目标路径，与既有 `ops.file.upload` 口径一致）。

### 3.7 前端

- 新页「审批中心」（菜单按 `approval:read` 显隐）：**待我审批 / 我的申请**两个 Tab；
  列表 + 详情抽屉 + 审批链时间线——形态照告警页（`AlertsView.vue:462,534-589`）。
- `OpsView.vue` 提交后按响应区分：201（已下发）/ 202（**已提交审批**）；
  文案必须不同，并在 202 时给出审批单号与"去哪儿看"。
- 配置页放在同一页的「设置」Tab（照保留策略那种"保存即生效"的形态）。

### 3.8 配置

独立配置文件（照 `RetentionFile` 惯例，Web 可改、保存即热生效）：

```yaml
approval:
  enabled: false          # 默认关闭，见 D2
  requireFor:             # 受管动作（默认：会改变远端状态的那些）
    - ops:svc.restart
    - ops:file.push
    - defense             # fail2ban 处置下发
    - system:upgrade
    - agent:upgrade
  ttlMinutes: 30          # 审批单有效期（与 ops 任务 TTL 同口径）
  maxRequests: 500        # 上限，只淘汰终态
```

## 4. 决策点（D1~D10，均给建议与理由）

| # | 问题 | 建议 | 理由 |
|---|---|---|---|
| **D1** | 审批范围 | 只覆盖**会改变远端状态**的动作（写类 ops 动作、fail2ban 处置、两种升级）；**只读动作（`node.diagnostics`/`svc.status`/`container.*` 查询）不审批** | 只读动作没有破坏力；给排障查询加审批，结果是大家绕开审批去用别的入口，反而更糟 |
| **D2** | 默认开关 | **默认关闭**（`enabled: false`） | 单管理员部署下若默认开启，**任何动作都将永远无法执行**（没人能批）。开启必须是管理员的显式决定；关闭时行为与今天**完全一致**（回归零风险） |
| **D3** | 批准后怎么执行 | **自动执行**，审批单自带动作 | 否则"批了但没人执行"成为新的糊涂账；且再点一次会引入"第二次点的参数和第一次不一样"的漏洞 |
| **D4** | 不可自批 | **硬规则**：申请人 ≠ 审批人；批准需 `approval:approve` **且**持有动作本身的权限 | 双人复核的全部意义在此；"批自己"等于没批 |
| **D5** | 超时 | 默认 **30 分钟**失效，过期**不执行**、需重新申请 | 与 ops 任务 TTL 同口径；一个三天前的批准不该还能把机器重启 |
| **D6** | 资源范围 | 申请人与审批人**都**按节点范围校验 | 与全站范围口径一致；审批是最容易漏范围的地方之一 |
| **D7** | 存储 | **新建** `internal/server/approval/` store（照 ops store 的双模式 + TTL + prune）；**不改 ops 状态机** | 改 ops 要同时动 `Take`/`prune`/`OpsStateTerminal`/`FileRefInUse` 四处，漏一处就是状态不落盘；两件事分开更安全 |
| **D8** | 留痕 | 每次流转写审计（含 `executed` 把审批单与 ops 任务号接起来） | 验证矩阵用例 7-07 明确要求"审计记录审批链" |
| **D9** | 不可篡改审计 | **本批不做**，且**不声称**前置条件已齐 | §3.4 后第 4 条那对前置条件针对的是"**放开任意执行**"。本批没有放开——仍是参数化动作、参数仍由两端校验。这条差别必须写清楚，否则以后会误以为"双人复核做了，exec 就可以上了" |
| **D10** | 前端位置 | 新页「审批中心」；提交侧改文案区分 201/202 | 告警页已证明"列表 + 抽屉 + 时间线"够用，不新建组件体系 |

## 5. 批次划分（三笔）

1. **审批内核**：`internal/server/approval/`（实体 + 状态机 + 存储 + TTL/prune）＋ 权限点与内置角色 ＋ 用例。
2. **接入与接口**：`needsApproval` 收口 ＋ 五处入口接入（ops 单发/批量、处置、两种升级）＋ 审批 API ＋ 审计 ＋ 用例。
3. **前端与文档**：「审批中心」页 ＋ `OpsView` 文案区分 ＋ 配置页 ＋ 文档对账。

## 6. 实机验证计划（dev-server）

判据里前三条**直接取自验证矩阵用例 7-07**：

1. **不可自批（决定性）**：申请人自己调 approve → 拒绝（403/409），且**动作从未下发**；
2. **超时自动失效（决定性）**：把 TTL 临时调成 30 秒 → 等过期 → 再批准 → 拒绝，**ops 任务列表里没有这条**；
3. **审计记录审批链（决定性）**：提交/批准/执行三条都在，`Detail` 能串起"谁申请、谁批、成了哪个任务"；
4. **批准后自动执行**：批准 → ops 任务出现且 `Operator` = **申请人**（不是审批人）；
5. **范围**：受限账号提交范围外节点被拒；范围外的审批人**看不到**该申请、直接调 approve 也被拒；
6. **关闭开关后行为与今天完全一致**（回归：提交即下发，不产生审批单）；
7. **只读动作不被拦**（`node.diagnostics` 在开启审批时仍直接下发）。

**未覆盖边界（不得视为通过）**：

- **双人复核挡不住"中心被攻破"**：审批人也是中心里的账号，攻破中心即可伪造两个人。这是本能力的**真实边界**，
  必须写进文档而不是回避——它防的是**误操作与单账号被盗**，不是防有备而来的攻击者。
- **不可篡改审计未做**（D9）；**多实例/HA 未做**（审批单是单机存储，与 A1 暂缓同因）。
- 浏览器实点（审批中心交互、时间线渲染）只做人工确认，不进自动判据。
