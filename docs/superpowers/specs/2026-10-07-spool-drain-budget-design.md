# 代理增强：补传排空预算与可见性（"批量合并"的另一半）设计件

- 批次：27
- 日期：2026-10-07
- 对应全景表：`2026-09-30-ops-platform-capability-map.md` 行 288「代理增强（磁盘缓冲/批量合并/主备）」，
  正文末尾「**批量合并与主备未做**」
- 状态：**设计待评审（D1~D8）**

## 1. 起因（先纠正一处对"未做"的理解）

行 288 说"批量合并未做"，但把代码读清之后是这样：

- **请求级的合并已经在做**：`Spool.Send`（`internal/agent/reporter/spool.go:199-219`）每一轮都会
  `Drain(512 KiB)` 取补传点，**追加**到本轮载荷的 `Metrics` 里（老点在前、本轮点在后），
  **一个请求**发出去。也就是说"把多条记录合并成更少的请求"这件事本身已经是现状。
- **真正没做的是"排空速度"与"排空过程的可见性"**：单轮补传上限是**固定常量** 512 KiB
  （`spool.go:46`），排空速率因此被钉死在 **2 MiB/分**（512 KiB × 4 轮/分，上报周期默认 15 s）；
  而 spool 上限默认 8 MiB（`config.go:267`）→ **一次长断网恢复后要约 4 分钟（≈16 轮）才排空**。
  期间只有 `agent_spool_bytes` 一个深度指标（`main.go:462-470`）+ 丢弃时的告警日志，
  **没有"这一轮补了多少、还剩多少"** 的过程信息。

所以本批要做的不是"合并"（已在做），而是：**把固定预算换成按真实上限算出来的动态预算（排得更快），
并让排空过程看得见**。

## 3. 范围

**做**：

1. **动态补传预算**：把固定 512 KiB 换成"按 Server 上限、本轮实际载荷体积、安全余量算出来的预算"，
   并保留一个**下限**（宁可慢，不可失败）；
2. **413 自愈**：万一还是撞上 413（Server 的实际上限比 Agent 以为的小），**把预算减半并记住**，
   下一轮自动用更小的预算——保证"永远不会因为预算过大而永久排不空"；
3. **排空可见性**：每轮记录"补传了多少字节/多少点、还剩多少"，累计成一个指标 + 一条 info 日志
   （现在只有深度指标与丢弃时的告警）。

**不做**（划线，并说明理由）：

- **同一序列的多点合并/降采样**（"只留最后一点"或按步长压缩）：**不做**。它会**主动丢弃真实样本**，
  改变曲线语义；而且 spool 层**没有序列维度**（一行是一轮的全部点），要做得先引入按序列聚合与
  "哪些点可安全丢"的判据——那是另一件事，且风险远大于收益。
- **主备**：**不做**，也不建议近期做。Agent 侧**无先例、无设计**；它要同时解决
  "两个 Agent 报同一节点怎么判重""谁 active / 心跳 / 脑裂怎么办"，而**Server 侧的高可用（A1）本身就暂缓着**——
  Agent 主备在没有 Server 主备的前提下只是半个故事。
- **提高 spool 上限**（8 MiB）：它是"保留最近多少数据"的产品取舍，与本批无关。

## 4. 设计

### 4.1 动态预算怎么算

```
budget = clamp(serverBodyLimit × safetyRatio − liveEstimate, minBudget, maxBudget)
```

- `serverBodyLimit`：**配置项**（`agent.yaml` 新增 `spoolServerBodyLimitMB`，默认 **16**）——
  与 Server 的默认上限一致；Server 改大了它也可以跟着改；
- `liveEstimate`：**上一轮实际发出的请求体字节数**（发送成功后记下来）。不用"本轮先 marshal 一次再决定"
  ——补传要在 marshal 之前定，而"上一轮的体积"是同一台机器、同一套采集项下最准的估计；
- `safetyRatio`：**0.5**（留一半余量）——上报体里有 JSON 结构开销、标签重复、以及**本轮会比上一轮更大**
  的可能（新增实例、长标签）；
- `minBudget`：**256 KiB**（比现在的 512 KiB 更保守的下限：即便估算失准也不会失败）；
- `maxBudget`：**8 MiB**（`serverBodyLimit × 0.5` 的自然上限，也避免单轮请求体过大）。

按这套算：默认环境下 `16 MiB × 0.5 − ~0.1 MiB ≈ 8 MiB` → **8 MiB 的积压一轮就能排空**（现在要约 16 轮）。

### 4.2 413 自愈

发送失败且状态码是 **413** 时：

- 把**当前预算减半**并记为"已知上限"（例如从 8 MiB → 4 MiB），**下一轮**用新预算；
- 连续 413 时继续减半，直到 `minBudget` 为止（**永不小于下限**，保证一定能排空）；
- 记一条 warn 日志（"Server 拒绝了大请求，补传预算降到 X"）——这是"Agent 与 Server 上限配置不一致"
  的唯一可见信号。

这一条是**安全网**：没有它，动态预算一旦估错就会重演 512 KiB 当初要防的那个坑
（"每一条都超限而永远失败"）。

### 4.3 可见性

- **指标**：新增 `agent_spool_drained_bytes_total`（累计补传字节）与 `agent_spool_drained_points_total`
  （累计补传点数）；深度指标 `agent_spool_bytes` 保持不动（它是"还剩多少"）；
- **日志**：每轮排空后 info 一行：`补传 3.2 MiB / 4200 点，剩余 4.8 MiB`；排空完成时另记一行
  （"缓冲已排空"）——这样运维不必只看一条曲线猜进度；
- **不做**专门的排空进度接口（那要 Server 侧配合，而 spool 是 Agent 本地的事）。

## 5. 决策点（D1~D8）

| # | 问题 | 建议 | 理由 |
|---|---|---|---|
| D1 | 范围 | **只做动态预算 + 413 自愈 + 可见性**；不做同序列降采样、不做主备 | 见 §3：合并已在做；降采样会丢真实样本；主备无先例且依赖暂缓的 Server HA |
| D2 | 预算算法 | `serverLimit × 0.5 − 上一轮实际体积`，夹在 [256 KiB, 8 MiB] | 留一半余量；用上一轮实测值而不是猜 |
| D3 | Server 上限从哪来 | **配置项**（默认 16 MiB，与 Server 默认一致） | Agent 无法探测；写死会在 Server 改配置时失配 |
| D4 | 撞 413 怎么办 | **减半并记住**，下限 256 KiB，记 warn 日志 | 这是"永不排不空"的兜底；也是配置失配的唯一信号 |

| D6 | 可见性 | 两个累计指标 + 每轮 info 日志（含剩余） | 现在只有深度曲线，看不出"排到哪了" |

## 6. 批次拆分、用例与实机验证

### 6.1 两笔

1. **预算与自愈**：`spool.go` 把固定常量换成"可传入的预算 + 413 减半状态"；`Send` 记录上一轮体积；
   `config.go` / `agent.yaml` 新增 `spoolServerBodyLimitMB`（默认 16）。
   用例：预算算法（正常估算、上一轮体积很大时降到下限、serverLimit 很小时不越界）、
   413 减半并持久到下一轮、连续 413 直到下限、非 413 失败**不**改预算。
2. **可见性**：两个累计指标 + 每轮日志。用例：累计值随补传增长、排空完成时日志出现。

### 6.2 实机验证计划（dev-server）——**这次只需升 Agent**

造长断网是可行的：把 Agent 的上报地址指到一个**不通的端口**（或 `systemctl stop monitor-server` 更狠，
但那样就验不了恢复后的排空 ✗ → 用前者：改 `agent.yaml` 的 `server` 指向一个黑洞端口 → 断网若干分钟
→ 让 spool 长到接近 8 MiB → 改回 → 观察：

1. **一轮排空（决定性）**：恢复后**第一轮**就把积压基本排完（`agent_spool_bytes` 从 ~8 MiB 掉到接近 0），
   而不是现在的十几轮；
2. **不撞 413**：全程没有 413（Server 日志与 Agent 日志都不出现）；
3. **数据不丢**：时序库里能查到断网窗口内的点（沿用当初 7 小时断网那次的判据）；
4. **可见性**：日志里有"补传 X / 剩余 Y"，指标 `agent_spool_drained_bytes_total` 增长；
5. **下限兜底（负例）**：把 `spoolServerBodyLimitMB` 配成 **1**（远小于真实 16）→ 预算被夹到下限附近，
   仍然**排得空**、不失败。

**未覆盖边界（不得视为通过）**：413 自愈的**真实触发**（要真让 Server 拒一次大请求——本机 Server 上限
16 MiB，除非临时把它调小，那要改 Server 配置并重启，列入"可选"）；多 Agent 并发上报时 Server 的总体压力；
浏览器实点（本批无前端）。

## 8. 实施记录（2026-10-07，Agent 1.30.49）

两笔都已落地（D1~D8 全部按建议）：

**① 预算与自愈**：`internal/agent/reporter/spool.go` 把固定的 `maxSpoolDrainBytes`（512 KiB）
换成 `spoolDrainCeiling`（8 MiB）/ `spoolDrainFloor`（256 KiB）与 `drainBudget(livePoints)`
（= `serverBodyLimit/2 − 非指标部分估算 − 点数 × 单点估算`，再夹紧、再受 413 学到的小上限约束）；
`OpenSpool` 多收一个 `serverBodyLimit` 参数；`noteFailure` 只在 **413** 时把学到的小上限**减半**
（下限兜底、记 warn）；`reporter.go` 新增**带状态码的错误类型** `HTTPStatusError`
（此前是 `fmt.Errorf` 拼字符串，靠它判 413 会在改一次文案后静默失效）；
`config.go` 新增 `spoolServerBodyLimitMB`（默认 16，与 Server 默认一致）并接进 `cmd/agent/main.go`。

**② 可见性**：新增 `DrainedBytes()` / `DrainedPoints()` 两个累计量，`cmd/agent/main.go` 把它们
连同原有的 `agent_spool_bytes` 一起作为自监控指标上报；`noteDrained` 每轮记一行
`已补传缓冲数据 drainedKB=… points=… remainingKB=…`，排空那一刻另记 `磁盘缓冲已排空`。
配置手册（`docs/configuration-cookbook.md` §五）补上了新字段与它的两条边界（配小只是慢、配大有兜底）。

**测试**：`go test ./...` 全绿。新增 3 条（`spool_budget_test.go`）：预算的四种边界
（默认 / 上限更大时顶到上限 / 上限小时夹到下限 / 载荷估算超过上限时不出现负预算）、
413 逐次减半直到下限**且学到的小上限不会回升**（同时验证**非 413 的失败不动预算**）、
以及**决定性的一条**：同样积压下新预算一轮排掉的量**远多于旧的 512 KiB**，且**请求体不超 Server 上限**
（补传预算的全部意义就是这两条同时成立）。既有 `spool_test.go` 随接口更新（常量名与 `OpenSpool` 第三参数）。

**实施中自己踩的坑**：新用例第一版把"预算"期望成正好等于上限——实际是
`上限/2 − 载荷估算`，默认 16 MiB 环境下是 8 MiB **减掉** 256 KiB + 点数×256（不会顶到上限）；
另一版又让 8 MiB 积压去断言"一轮排空"，而预算只有约 7.6 MiB——**"一轮排空"只在积压 ≤ 预算时成立**。
两处都是我的期望写错，代码没错；改成"上限更大时才顶到上限"与"灌 3 MiB 验一轮排空"后全绿。

**未覆盖（不得视为通过）**：413 自愈的**真实触发**（要真让 Server 拒一次大请求——本机 Server 上限
16 MiB，除非临时改小并重启，列为可选）；多 Agent 并发上报时 Server 的总体压力；
浏览器实点（本批无前端）。
