# 审计防篡改（链式 HMAC + 锚点 + 校验）设计件

- 日期：2026-10-08
- 对应全景表：§3.4「操作面安全边界」第 4 条的**前置条件之一**（"双人复核 + **不可篡改审计**"）
- 版本：1.30.55（Server 单侧）
- 状态：**待评审**（D1~D8）

## 1. 起因

§3.4 边界第 4 条写着：**"若将来确实要放开任意执行，前置条件是双人复核 + 不可篡改审计"**。
双人复核已于 1.30.50 落地（`internal/server/approval/`），**审计这一半没做**。

而**本设计件必须先纠正一处我自己的过期陈述**：我此前说"审计落在 `audit_events.json`（2000 条上限、
可被删除）"——那是**降级模式**。现状早已是 **SQLite 入库**（批次 18），
保留口径是**时间 180 天 + 兜底 50 万行**。事实见 §3。

更要紧的是：**既有设计件已经明确写过"入库 ≠ 防篡改"，并且要求"不要把入库说成审计更安全了"**
（`2026-10-05-audit-ack-persistence-design.md` §5）。那条结论今天仍然成立，本设计件**不推翻它**，
而是把它剩下的部分补上——并同样**不夸大**。

## 2. 目标与非目标

### 2.1 目标：**篡改与删除"可检测"**

今天的审计**没有任何完整性校验**：改一行、删一行，**谁也看不出来**。本设计要让"动过审计"这件事
**留下可验证的证据**。

### 2.2 非目标（**不得声称**）

- **不是"不可删除"**。库文件仍在该机、同一权限面下，root 依然能删。本设计给的是
  **可检测**，不是**不可为**。命名上一律用「**防篡改（可检测）**」，**不用「不可篡改」**。
- **不补齐 §3.4 的前置条件**。前置要求的是"不可篡改"；本批做到的是"**可检测**"，
  两者**不是同一件事**。因此本批结束后，**§3.4 第 4 条的前置仍标注为未补齐**（见 D1）。
  真正的"不可删除"需要**只追加的外部存储**（异地 syslog / 对象存储的对象锁）——
  既有设计件已判定那是"另一个量级的工程"，本批不碰。
- 不解决"业务已提交、审计未落链"的中间态（审计与业务**不同事务**是既有设计，
  RequestID 方案正是为规避跨包事务而生，见 `api/audit.go:27-30`）。

### 2.3 威胁模型（**先讲清防哪一档**）

| 场景 | 攻击者能做什么 | 本设计 |
|---|---|---|
| A 库被复制/泄露后改一份 | 有完整 DB，**没有密钥** | ✓ **检出**（HMAC 无法伪造） |
| B 改某条审计 | 有 DB 写权限 | ✓ **检出**（该行 HMAC 不匹配） |
| C 删中间某条 | 有 DB 写权限 | ✓ **检出**（`seq` 缺口 + 链断） |
| D 删尾部若干条 / 清空表 | 有 DB 写权限，**没有日志权限** | ✓ **检出**（靠**日志锚点**，见 §4.4） |
| E 拿到该机 root | 能改库 + 能读密钥 + 能清日志 | ✗ **防不住** |

**D 与 E 是这条防线真正的边界**：没有外部锚点，删尾部/整表在库内是"不可检测"的
（链的尾部天然没有后继来指认它）。所以 §4.4 的锚点是**必需项**，不是可选项。
而 E 档——root 能同时拿到密钥与日志——**本设计不声称能防**。

## 4. 设计

### 4.1 链的形态

`audit_events` 增加三列（`ensureColumn` 后补，纯附加、不升 `schemaVersion`——既有约定）：

```sql
seq        INTEGER NOT NULL DEFAULT 0   -- 单调递增的链序号（不复用 id：见下）
prev_hash  TEXT    NOT NULL DEFAULT ''  -- 上一条的 hash（链头为空串）
hash       TEXT    NOT NULL DEFAULT ''  -- HMAC(key, seq|prev_hash|规范化字段)
```

**为什么另起 `seq` 而不用自增 `id`**：`id` 会因删除而出现缺口，而缺口既可能是裁剪（合法）
也可能是篡改（非法）——用 `id` 当链序号，**两种缺口分不开**。`seq` 由**链状态表**单独维护，
裁剪只记录"哪一段被合法移除了"（§4.3），于是校验时**缺口能被归因**。

**hash 覆盖哪些字段**：`time_ms | user_name | method | path | status | remote_ip | source_loc |
succeeded | category | action | detail | request_id` + `seq` + `prev_hash`。
（即**全部业务列**——少覆盖一列，那一列就成了可改而不被发现的字段。）

### 4.2 密钥

- 独立文件 `/etc/monitor-server/audit.key`（**0600、root**），首次启动自动生成 32 字节随机值。
- **绝不放进 `server.yaml`**：那个文件常被复制、备份、贴进工单。
- **绝不通过任何接口返回**：接口只返回"是否已启用""密钥指纹（前 8 位哈希）"，不返回密钥本身。
- **密钥丢失 = 历史不可验**（这是真陷阱）：校验结果必须**区分**"某条被改"与"密钥不匹配"——
  前者是安全事故，后者多半是换了机器/换了密钥。**把后者报成前者会造成假警报**。
  接口返回里带**密钥指纹**，历史校验失败时用它判断。

### 4.3 裁剪与链（**本设计最关键的一处**）

链与裁剪天然冲突：裁剪删掉最老的若干条，链在裁剪点必然"断"。做法：

- 新增单行状态表 `audit_chain(seq, hash, key_fingerprint, updated_ms)`——**当前链头**。
- 新增 `audit_pruned(from_seq, to_seq, head_hash, pruned_ms)`——**每次裁剪记录被合法移除的那一段**
  （含该段末尾的 hash）。
- `Prune` / `PruneRows` 在删除**之前**先算出被删的 `seq` 区间与末条 hash，写进 `audit_pruned`
  （**同一事务**：要么都成，要么都不成——否则会出现"删了但没记"，下次校验就是假警报）。
- 校验规则：现有行的链自洽 ✓；**最老那条的 `prev_hash`** 必须等于 `audit_pruned` 里对应区间末尾的 hash ✓；
  **中间任何缺口**必须能在 `audit_pruned` 里找到对应区间 ✓，否则报"**无法归因的缺口**"。
- 顺带把 `PruneRows` 的保留口径从"按 `time_ms` 最新"改为"**按 `seq` 最新**"：
  它是**条数兜底**、不是时间规则，按到达顺序（seq）才是它本来的语义，
  而且这样裁剪永远是**前缀**、不会从中间挖洞（时间戳偏斜是真实存在的，见 §3 事实表）。

### 4.4 锚点（**必需项**，不是可选项）

库内链**无法**证明"尾部没被删"（尾部没有后继指认它）。因此：

- 服务**周期性**（每 N 分钟或每 N 条，取先到者）把链头写进**服务日志**：
  `audit chain head seq=<n> hash=<h> keyfp=<fp>`。
- 日志是**另一个权限面**（journald），且可被运维**送往异地**——攻击者只改库不改日志，
  校验就能发现"库里的链头比日志里记录的那条**更短或不同**"。
- **成本极低**（一条日志/几分钟），**默认开启**。
- **如实说明**：这仍然不是"不可删除"——拿到 root 的人能连日志一起清。它抬高的是
  **"只攻破应用/数据库这一层"**的门槛（场景 D）。

### 4.5 校验接口

`GET /api/v1/audit/verify`（权限 `audit:read`，见 D5）：

```json
{
  "enabled": true,
  "mode": "sqlite",
  "keyFingerprint": "a1b2c3d4",
  "verifiedFrom": 1201, "verifiedTo": 48213,
  "rowsChecked": 47013,
  "prunedSegments": [{"from": 1, "to": 1200, "headHash": "…"}],
  "ok": true,
  "breaks": []
}
```

**报告口径必须诚实**（这是最容易做错的地方）：

- **报出覆盖范围**（`verifiedFrom..verifiedTo` + `rowsChecked`），**不只报"通过"**——
  "已验证 47013 条"与"全部通过"是两句话，后者在这套机制下**永远不成立**（历史已被裁剪）。
- 断裂点逐条列出：`seq`、原因（`hash-mismatch` / `unattributable-gap` / `prev-hash-mismatch`）。
- 密钥不匹配单独一种原因（`key-mismatch`），**不与"被篡改"混为一谈**。
- 降级模式返回 `enabled:false` + `mode:"json"` + 一句**明确的**"当前为降级模式，**无完整性保护**"。

### 4.6 导出带链摘要

CSV 导出（`audit:export`）在响应头与文件末尾附上**该次导出覆盖的区间与链头 hash**，
使**第三方离线核对**成为可能（拿到 CSV 与锚点日志即可判断这段历史是否被动过）。
不在 CSV 里逐行加 hash 列——那会让导出变成"hash 表"，反而没人看内容。

### 4.7 降级 JSON 模式

**不启用链**（它的写入是整文件重写，与链式追加语义不兼容），并在接口与界面**明确标注**。
**不假装降级模式也有保护**。

### 4.8 前端

审计页加「完整性校验」按钮 + 结果卡片：覆盖区间、条数、断裂点（若有）、密钥指纹；
降级模式显示明确提示。**断裂时用醒目样式**（这是本页唯一"红色"该出现的地方）。

## 6. 实机验证计划（dev-server）

1. **正常态（决定性）**：`GET /api/v1/audit/verify` → `ok=true`，报出**覆盖区间与条数**（不是只说"通过"）；
2. **改一行（决定性）**：直接 `sqlite3 UPDATE audit_events SET detail='...' WHERE id=<某条>` →
   校验**必须报出该 `seq` 的 `hash-mismatch`**，且 `ok=false`；**改回后恢复 `ok=true`**；
3. **删中间一行（决定性）**：`DELETE` 掉中间某条 → 校验报 **`unattributable-gap`**（不能只说"失败"）；
4. **裁剪不算篡改（负例，最容易被做错）**：手动触发 `POST /api/v1/system/retention/cleanup` →
   校验**仍然 `ok=true`**，且 `prunedSegments` 里能看到那段被合法移除的区间
   ——**这一条防的是"把正常裁剪报成被人删了"的假警报**；
5. **锚点**：日志里能查到 `audit chain head seq=… hash=…`；
6. **密钥**：`audit.key` 是 0600、且**任何接口都不返回密钥**（只返回指纹）；
7. **降级模式**：把库路径指到不可写处 → `enabled=false` + 明确提示"无完整性保护"。

**未覆盖边界（不得视为通过）**：场景 D 的真实对抗（要模拟"攻击者清了库但没清日志"）；
场景 E（root）本设计**不声称能防**；多实例；导出 CSV 的第三方离线核对（只验接口与头部字段）。

## 8. 实施记录（2026-10-08，1.30.55）

四笔都已落地，D1~D8 全部按建议执行。**改动面：Server + 前端**（Agent 未改，**只需升 Server**）。

| 落点 | 实现 |
|---|---|
| 表结构 | `audit_events` 加 `seq / prev_hash / hash / key_fp`（`ensureColumn` 后补、**不升 `schemaVersion`**）；新表 `audit_chain`（链头单行）、`audit_pruned`（裁剪区间 + 自己的 HMAC） |
| 密钥 | `internal/server/audit/chain.go` 的 `LoadOrCreateChainKey`：独立文件、0600、32 字节随机、十六进制文本；配置项 `auditKeyFile`（默认 `/etc/monitor-server/audit.key`） |
| 链写入 | `Store.appendChained`：**读链头 → 算 HMAC → 插行 → 更新链头，全在一个事务里**（分两步写会留下"行插了但链头没动"，下一条就用同一个 seq，链当场错位） |
| 签名 | `chainDigest` 用**结构体**（不是 map）序列化，覆盖**全部 12 个业务列** + `seq` + `prev_hash` |
| 裁剪 | `Store.pruneWhere`：先统计被删的 seq 区间与该段末条 hash，**与删除同一事务**记进 `audit_pruned`（带 HMAC）；`PruneRows` 口径从「按 `time_ms` 最新」改为「**按 `seq` 最新**」 |
| 锚点 | `Store.RunAnchor`：每 5 分钟把链头写进服务日志，消息用 ASCII `audit chain head`（给脚本与运维 grep 的稳定标记） |
| 接口 | `GET /api/v1/audit/verify`（`audit:read`）；报告带 `verifiedFrom/To`、`rowsChecked`、`unchainedRows`、`keyMismatchRows`、`linkUnverifiedRows`、`prunedSegments`、`truncated`、`breaks` |
| 前端 | 审计页「完整性校验」按钮 + 结果卡（三档：通过/未启用/异常）+ **常驻**一行边界说明"这是可检测、不是不可篡改" |

**实施中的五处判断**：

1. **另起 `seq` 而不用自增 `id`**：`id` 的缺口分不清"裁剪"与"篡改"；`seq` 配 `audit_pruned` 才能**归因**。
2. **每行记 `key_fp`（签名密钥指纹）**：没有它，换了密钥（恢复备份、换机器）会**全部报成"hash 不匹配"**
   ——那是假警报，会被当成有人改过审计。有它就能分开报"密钥不匹配"与"被篡改"。
3. **裁剪记录自己也要带 HMAC**：否则有库写权限的人可以**伪造一条裁剪记录**来遮盖自己的删除；
   有了 HMAC 他伪造不出（没有密钥），只能删——而删掉记录会让缺口"无法归因"，照样被检出。
4. **`PruneRows` 改按 `seq`**：它本是**条数兜底**、不是时间规则，按到达顺序才是原意；
   而且按 `time_ms` 排会在时间戳偏斜时**从中间挖洞**，那会让正常裁剪被报成"有人删过审计"。
5. **指纹在降级模式也返回**：它不是秘密，而运维要靠它确认"服务器手上是哪把密钥"——
   换过密钥却没对上时，这是唯一能看出来的地方（第一版把它写在 `db != nil` 分支之后，降级模式就漏了）。

**用例 26 条**：`internal/server/audit` 本次新增 **19 条**——链与密钥 8（0600、重启复用、短文件拒绝、

## 9. 实机结果（2026-10-08，dev-server 升 Server 1.30.55）

`dist/audit-tamper-e2e.py core`（**需 `sudo python3`**，理由见下）：**14 项断言全过 / 0 失败**。

| 判据 | 实测 |

**必须如实报告的一次真实损失**：本核对脚本的**早先版本**在收尾时用「`DELETE` 全表 + 按备份整体重插」
做还原 ✗，于是**抹掉了核对期间服务端新写的 3 行真实审计**（seq 7..9，即那次运行的登录、
改保留策略、触发清理三条留痕）。后果是**该机审计链上留下一处永久缺口**，
`GET /api/v1/audit/verify` 会一直如实报 `unattributable-gap`（第 7..9 条）。

**我没有把它伪造成一条裁剪记录** ✗——那才是真正的作假，等于亲手废掉这套机制的意义。
这条缺口是**真实的、由一次非保留策略的删除造成的**，它被报出来**恰恰说明机制在正常工作**。
脚本已改为**只补缺失行、绝不删除**（`restore_rows`），并在文件头与函数注释里写明这次教训。

**核对脚本自己踩的五个坑（都是脚本，不是产品）**：

1. **`assets.db` 是 `root:root 0644`，脚本必须以 root 运行** ✗——以普通用户跑报
   `attempt to write a readonly database`。已加**写前预检**（`BEGIN IMMEDIATE` + `ROLLBACK`，
   不改变数据）与可操作提示。
2. **本机 sudo 得到的 root 在用户命名空间里是重映射的** ✗——它能新建文件，但**写不了属于
   `ubuntu` 的文件**（对那个 0644 文件来说它是 "other"）。固定名备份因此写不进去；
   改用 `tempfile.mkstemp`（每次独立、归属一致）。
3. **`restore_rows` 用「整体重插」会毁掉核对期间的新审计** ✗——见上，已改为只补缺失。
4. **`sqlite3.Connection` 没有 `description`** ✗（在 cursor 上）；**`stat -c '%a'` 里的 `%a`
   被 Python 当成格式占位符** ✗（要写 `%%a`）。
5. **判据不能锚在全局 `ok` 上** ✗——机器上已有那条真实缺口时，`ok` 恒为 false，
   于是"改回后恢复通过"这类断言必然红。已全部改为**锚定到具体那一行**（某 seq 的某个 reason）。

**未覆盖（如实划线）**：

- **「裁剪不算篡改」这一支在真机上打不中** ✗：链上记录都是当天的，而保留窗口单位是"天"
  （最小 1 天），所以没有超期行可裁。第一版曾把窗口临时调成 1 天 ✗，结果**真的删掉了约 4736 行
  老审计**（收尾补回）却**没产生任何裁剪区间**——超期的都是**未上链**的历史行（`seq=0`），
  而它们本就不产生链区间：**只有折腾、没有覆盖** ✗。已改为不动窗口，并如实标注这一支
  **只有用例覆盖**（`Prune` 与 `PruneRows` 各一条）。
- 场景 D 的真实对抗、场景 E（root，本设计不声称能防）、多实例、导出 CSV 的第三方离线核对。
- ~~一处已知小缺口：锚点是每 5 分钟写一次，服务刚启动到首次 tick 之间没有锚点。~~

## 已知历史缺口（dev-server，2026-10-22 复核）

dev-server 的审计链在 **`seq` 7..9** 有一处**无法归因的缺口**（`id` 5438–5440 缺失），
`audit_pruned` 中没有任何对应区间，因此完整性校验会持续报 `ok=false`：

```
第 7..9 条不见了，且不在任何合法裁剪记录里
```

**已确认与迁移无关**：迁移前的 SQLite 备份（`assets.db`）里同样缺这三行、`audit_pruned`
同样为空。缺口形成于链功能早期（2026-10-08 之前），设计件当时的验证记录里也提到过
「机器上已有那条真实缺口」。

**决定（2026-10-22）：保留现状，不补记裁剪锚点。** 补记等于在审计账本上追加一笔
"这些行是合法丢失"的声明，而事实并非合法裁剪；让校验如实报告，比让人以为账本完整更重要。
**代价**：该部署的校验页会一直显示这条缺口——运维需要知道它是已知历史问题，不是新事故。
