# 减重与值班台（阶段 1）设计

- 日期：2026-10-19（2026-10-20 确认决策）
- 状态：已确认（D1~D8 均按推荐）
- 归属：用户 2026-10-19 提出的「系统笨重 + 缺乏智能化」改造的第一个阶段
- 一句话：**不推倒重来**——把 101 个功能点平铺成的菜单收成「值班台 + 按需开启的模块」，并把「我该做什么」提到首页。

## 1. 起因与用户口径

用户 2026-10-19 的原话是三个方向同时成立：**使用上重**（菜单多、找不到东西）、**组件多**（部署与维护成本）、**代码维护重**（加功能牵一发动全身）；目标环境是**政务云**（多数不能访问外网，开外网需单独申请策略）；另外**缺智能化**——「人尽量少参与，AI 负责的多一些，但敏感操作或者数据还是人来做」。

三条已拍板的边界（本轮原文确认，不要再问）：

| # | 事项 | 用户拍板 |
|---|---|---|
| 1 | 模型来源 | 政务云自带的模型服务，或阿里云/腾讯云等厂商的 API（**远端 OpenAI 兼容接口**，不是用户自建 GPU） |
| 2 | 自动化边界 | **诊断不需要人参与**；**要解决问题时才需要人参与** |
| 3 | 本轮范围 | **先做阶段 1**（模块开关 + 值班工作台 + 菜单收起），不动架构 |

第 1 条有一个直接后果要记住：模型是**云端 API**，所以已有的「数据出境」口径（`ai:invoke` 单列、数据分级、每次调用写审计）在 AI 值班里**继续有效**，并且会变得更关键——如果 AI 开始自动调查，调用频次会从「人点一次」变成「每条告警一次」。

## 4. 设计

### 4.1 模块开关

#### 4.1.1 载体：复用 `uicfg`，不新建配置文件

`uicfg` 已经是「运行时改、保存即生效、独立小文件」的形态，且已有 `GET/PUT /api/v1/ui/settings` 与设置页（`BrandSettingsSubView.vue`）。模块开关的本质也是「界面上显示哪些功能」，与品牌同属界面配置。

**为什么不再开一个 `modules.yaml`**：这个项目已经反复吃过「同一件事两份定义必然漂移」的亏（`asset.ScopeSnapshot` 与 `report.ScopeSnapshot`、`danger.go` 的目录清单）。多一份配置就多一处要在升级文档、回滚说明、部署脚本里同步。

**关键兼容性质**：`uicfg` 的解析是「缺字段取零值」。因此用**关闭清单**（`disabled: []string`）时，旧 `ui.yaml` 没有这个字段 → 解析出 `nil` → **全开**，升级零迁移、无感。

#### 4.1.2 语义：用「关闭清单」而不是「开启清单」

```go
// Disabled 是被关闭的模块与页面（key 见 ModuleKeys）。
//
// **用关闭清单而不是开启清单**：全量开启时不需要任何配置，且**升级新增的页面会自动出现**。
// 若用开启清单，存量部署升级后新功能会静默不可见——那是最糟的形态（装了这个功能却没人知道）。
Disabled []string `yaml:"disabled" json:"disabled"`
```

同理，**不做「卸载模块」**：关掉菜单**不注销**后端路由。

理由（这条要写给将来想改的人）：注销路由会把「产品减重开关」变成「安全边界」，而它不是——真正的卸载是**不装**，`discover` 一个被关掉的接口能拿到 401 是"正常"、拿到 200 是"漏了"。这两件事混淆之后，下一次有人把「关掉资产模块」当成「资产数据对外不可达」就会出事。所以开关的定位在界面上要**明说**：关闭仅隐藏入口并停止对应的定时任务，**不影响已产生的数据，也不改变接口可达性**。

#### 4.1.3 粒度与清单

按**域**为主（域 = 侧栏分组），域内允许**单页**关闭（对应 `Sidebar.groups[].items[].key`）：

| 域 key | 名称 | 可整域关闭 | 说明 |
|---|---|---|---|
| `monitoring` | 观测监控 | 是 | 主机/中间件/容器/日志/拨测/指标浏览/自定义仪表盘 |
| `assets` | 资产与配置 | 是 | 台账/关系视图/配置项模型/配置巡检 |
| `ops` | 运维操作 | 是 | 节点操作/审批中心 |
| `alerting` | 告警运维 | **否**（仅可关组内单页） | 告警中心是核心，见下 |
| `security` | 安全治理 | 是 | 安全中心/操作审计 |
| `system` | 系统设置 | **否** | 关掉会把管理员锁在门外 |

**不可关闭清单（硬编码，服务端保存时校验并拒绝）**：

- `overview`（值班台）、`alerts`（告警中心）、`system`（系统设置全组）
- 理由：前两个是「发现与处置」这条主线的两端，关掉等于关掉监控本身；第三个是**唯一能把它改回来的入口**——允许关掉它，配置错一次就只能改文件，而在政务云里"上机器改文件"比点两下贵得多。

服务端校验放在 `uicfg.Save`，返回 400 并说明是哪一项不可关（静默剔除会让用户在界面看到"保存成功"但开关又弹回来）。

#### 4.1.4 影响面：三处，缺一不可

| 影响面 | 做法 | 不做会怎样 |
|---|---|---|
| ① 侧栏与命令面板 | 前端 `useModules` store 读 `disabled`，`Sidebar` 与 `CommandPalette` 过滤 | 菜单还在，等于没关 |
| ② 路由守卫 | `router/index.js` 增加一条判定：目标页所属模块被关 → **重定向首页并 `ElMessage.info` 说明原因** | 深链/收藏夹仍能进，用户以为没生效 |
| ③ 后台定时任务 | 巡检调度、报表定时、拨测执行前查询开关，关闭则**跳过本轮并记录原因**（不删数据、不改历史） | 任务照跑：报表每天生成、巡检每天落库，而没人看得到=无声浪费 |

第 ③ 项的**跳过要可见**：`slog.Info("模块已关闭，跳过执行", "module", key)`，且不在页面上报警。这与既有「日志/限额类丢弃按正常结果处理」同口径——把配置导致的行为记成 error，会让真问题被淹掉。

#### 4.1.5 顺手修的既有缺陷：保存站点设置会清空侧栏副标题

- 前端**会发** `subtitle`：`useBrand.js:69`（`payload.subtitle = subtitle`）。
- 后端 body **没有这个字段**：`internal/server/api/ui.go:23-27` 只解 `Name/Logo/Footer`，`Save(uicfg.UIConfig{Name, Logo, Footer})` 的 `Subtitle` 是零值 → 落盘为空串。
- 症状：用户在设置里改副标题并保存，提示「已保存，全局即时生效」，**副标题反而消失**（连原来的默认值「运维平台」一起没）。

修法：body 加 `Subtitle` 字段并透传。同时给 `handleUIPut` 补一条用例（保存时不传 subtitle 应保留原值还是清空——**按前端契约应当原样透传**，两者都传即无歧义）。

#### 4.1.6 界面

设置页新增「功能开关」区（`SettingsView` 的子视图，与品牌/大屏同级）：

- 每个域一行，域内页面以多选框列出；域标题右侧一个总开关（关掉即整域关闭）。
- 不可关项显示为**置灰 + 原因**（不是隐藏——用户找不到「为什么没有告警中心这一项」会以为是 bug）。
- 顶部一句固定说明：**关闭仅隐藏入口并停止对应定时任务，不影响已有数据**。
- 需要 `system:config`（与既有 `PUT /api/v1/ui/settings` 一致），不新增权限点。

### 4.2 值班台（首页改造）

#### 4.2.1 待我处理的口径：**只放「需要人做决定才能推进」的事**

这是本设计的核心判断，宁可少放：

| 纳入 | 判据 | 数据来源 |
|---|---|---|
| **待确认告警** | 活跃且未 ack（`unacknowledgedAlerts`），有 `alerts:read` | `GET /api/v1/alerts?state=active` |
| **待我审批** | 别人提交的 `pending` 审批单，有 `approval:read` | `GET /api/v1/approvals`（默认就是待我审批 + pending） |
| **AI 建议待采纳** | （阶段 3 才有；本批不出现） | — |

**刻意不放的三类，以及原因**：

1. **巡检差异** —— `InspectFinding` **没有处置状态**（§3 已核实）。放进来就是一个永远不消减的红点：用户看两次之后就学会了无视它，而这个红点本来是首页最该信的东西。要放它，前置是先给差异项加处置状态机（独立批次）。
2. **失败的 ops 任务** —— 任务已经是终态，失败信息在任务详情里，**不需要人「处理」才能推进**，它属于「排查线索」而不是「待办」。放进待办会让列表长期挂着已经无人问津的旧失败。
3. **资产失联 / 中间件离线** —— 它们会以告警的形式出现（服务离线、实例不可用规则），重复计一遍只会让数字虚高。工作台显示的是「待办」，不是「所有异常」。

#### 4.2.2 数据获取：新增聚合接口，而不是前端并发

推荐 `GET /api/v1/workbench/summary`（新权限：无——按 principal 现有的 `alerts:read` / `approval:read` 分别收窄，缺哪个就返回该段 `available: false`）。

响应形状：

```json
{
  "todos": [
    {"kind": "alert",   "available": true, "count": 7, "items": [ ... ]},
    {"kind": "approval","available": true, "count": 2, "items": [ ... ]}
  ],
  "errors": [ {"kind": "approval", "message": "查询审批单失败"} ]
}
```

三条硬要求：

- **`available` 与 `count=0` 必须分开**：没权限/未启用审批 → `available:false`（界面显示「无权限」或不显示该卡片）；有权限但确实没有 → `count:0`（显示「没有待批」）。把两者混成 0，用户会以为「真的没人提交」。
- **单段失败不拖垮整体**：某段查询失败写入 `errors` 并继续返回其余段，HTTP 仍 200；**但为空不能被当成成功**——`available:true` + 失败必须在 `errors` 里同时出现，否则界面会显示「0 条待办」，对运维来说那是谎话（与审计查询「失败返回 500 而不是空列表」同一条道理）。
- **范围收窄在服务端**：复用 `filterByNodeScope` / `approvalInScope`，不在前端过滤。

**为什么不前端并发**：现有 `OverviewView` 已经在并发 5+ 个接口，再加 2 个并不难。但「待办」的语义是**跨域聚合 + 统一排序 + 按权限收窄**，如果前端逐接口拉，那么「这个用户看不到审批单」这条规则会写成前端的 `if`，而权限判断散在前端是过去吃过亏的地方（服务端仍会 401，但界面会出现"点了报错"）。聚合接口把这些收在服务端一处。

#### 4.2.3 页面结构

```
┌ 值班台（PageHeader：最近刷新 / 刷新按钮）
├ 待我处理                      ← 本批新增，占首屏最高位置
│   待确认告警 7 条  ─→ 告警中心（带 node 筛选深链）
│   待我审批   2 条  ─→ 审批中心
├ 系统状态：健康分 · 主机总览 · 中间件总览      ← 现有区块收敛
└ 最近告警（时序列表）                          ← 现有区块
```

- 「智能运维」区块**降级到系统状态区之后并默认收起**（现在它固定置顶且不可隐藏）。理由：它的定位是"解读"，而值班台首先要回答"我该做什么"；两者抢首屏时，"该做什么"必须赢。
- 现有 `useOverviewLayout` 的自定义布局能力**保留**（用户已习惯，且是本地存储、零成本），只把「待我处理」设为**固定置顶、不可隐藏**（与现在「智能运维」的 PINNED 机制同一处实现）。
- 空态明确：没有待办时显示「当前没有需要你处理的事项」，而不是留白。

### 4.3 菜单与可达性（「菜单收起」的正确做法）

#### 4.3.1 约束：不得回退成「按当前路由折叠」

`Sidebar.vue:253-256` 的注释是用户抱怨后的结论——22 个页面全靠逐层点开。本批**不能**通过「默认收起分组」来减重，那是在回退一个已经修过的问题。

「菜单收起」在本批 = **减少条目**（模块开关）+ **提高可达性**（下面两条），而不是折叠。

#### 4.3.2 常用置顶

- 侧栏顶部在「值班台」下方显示最多 5 个**固定**的常用页（星标），来源是用户自己勾选。
- 存储：先存 `localStorage`（与 `useOverviewLayout` 一致），不新增接口、不动 `uicfg`。
  - 已知代价：换浏览器/清缓存会丢。多设备同步需要进 `users.yaml`，那是第 ⑤ 项持久化迁移的活，不在本批。
- 已关闭的模块即使被置顶也**不显示**（开关优先级高于置顶，否则会出现"置顶能绕过开关"的怪现象）。

#### 4.3.3 命令面板

- 现状已经很好（从 router 派生，不会漂移）。本批只做两件事：
  1. 过滤掉被关闭模块的页面（与侧栏同一份 `useModules` 判定，不写第二份规则）。
  2. 顶栏搜索框的占位文案与快捷键提示对齐（`Ctrl/Cmd+K`）；`TITLES` 映射补上新增页面。

## 5. 明确的「不做」清单

| 不做 | 原因 |
|---|---|
| 注销被关闭模块的后端路由 | 把减重开关变成安全边界，见 §4.1.2 |
| 关闭模块时删除或隐藏已有数据 | 「关掉资产」不等于「删掉台账」。要删是独立的高危动作 |
| 为「待我处理」引入新的待办存储表 | 四类数据源都是**实时查询**即可确定的状态，存一份快照只会产生"待办与实际不一致"的新问题 |
| 巡检差异进待办 | 无处置状态机，见 §4.2.1 |
| 按模块拆数据库/表 | 与减重目标无关，反而增加运维面 |
| 权限模型改动 | 本批不新增权限点（`system:config` 已覆盖开关） |

| # | 决策 | 结论 |
|---|---|---|
| D1 | 开关载体 | **A 复用 `uicfg`（`ui.yaml`）** |

## 8. 验证口径

- **单测**：`uicfg` 保存时不可关项被拒（400 + 指明哪项）；旧 `ui.yaml`（无 `disabled`）解析为全开；`workbench/summary` 在「缺 `approval:read`」时返回 `available:false` 而不是 0；单段查询失败时其余段仍返回且 `errors` 非空。
- **组件用例**（真实 Element Plus 渲染）：关掉一个域后侧栏与该域菜单消失、命令面板搜不到、直接访问其路由被重定向首页；待办空态文案出现。
- **实机**（dev-server）：关掉「资产与配置」→ 侧栏消失、深链重定向、巡检定时任务日志出现「模块已关闭，跳过执行」；再打开 → 菜单恢复、**已有资产数据仍在**（这条是证明"关≠删"的决定性判据）。
- 界面类必须**真实浏览器走一遍**（不只组件用例），参照 `feedback_ui_verify_locally`。
