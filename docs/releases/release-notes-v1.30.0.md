# yingzhao-monitor v1.30.0 — 2026-10 资产与可观测收口、权限审计加固、下行操作护栏

**本版覆盖 1.29.0 ~ 1.30.56**（上一份发布说明是 v1.28.0，跨度较大，因此按**主题**而非逐版本罗列）。
五条线：**资产与配置**、**容器与集中日志**、**告警与报告**、**权限与审计**、**下行操作与护栏**。
**升级前请完整阅读「重要行为变化」与「运维动作」两节。**

**升级范围**：**Server、Web 与 Agent 都需要升级**——1.29 起 Agent 侧有多处采集与上报改动
（Pod 日志、K8s Service/EndpointSlice、MongoDB/MySQL 集群标识、补传排空预算、日志读取偏移持久化、
高危命令路径识别）。只升 Server 会缺这些能力，且部分界面会显示"未上报"。

## 一、重要行为变化（升级前必读）

- **资源范围新增「业务标签」维度**（与节点分组取**交集**，三态与节点维度同构）。服务端在资产域
  **读与写**上都强制。**若既有部署把"受限范围"当成仅隐藏菜单用，请检查这些用户实际应有的可见范围。**
  设计件 `superpowers/specs/2026-10-07-asset-business-scope-design.md`。
- **顺带关掉一条既有提权路径**：创建/更新用户与更新角色此前**不受**"范围不得超过操作者"约束，
  现在受约束。升级后，受限管理员不能再给他人授予比自己更宽的范围。
- **配置项模型的「缺失」改为按当前字段范围裁剪**（行为变更）：某字段被配成"运行态"后，
  它不再进差异清单、也不再报缺失；清空配置后恢复。设计件 `superpowers/specs/2026-10-07-asset-ci-model-design.md`。
- **审计与告警处置从 JSON 文件搬进台账库**（SQLite，同库单连接）。首次启动会把既有
  `audit_events.json` 一次性回填并改名 `.bak-migrated`（**不删**，既是证据也是回滚依据）。
  **回滚到旧版本后，旧版本读 JSON，审计与处置列表会是空的**——这是刻意的取舍（一个备份文件、
  一套迁移机制）。设计件 `superpowers/specs/2026-10-05-audit-ack-persistence-design.md`。
- **审计的条数兜底口径改了**（1.30.55）：按条数裁剪从"按 `time_ms` 保留最新"改为**"按 `seq` 保留最新"**
  （到达顺序）。原因：时间戳偏斜时按时间排会**从中间挖洞**，而链式防篡改会把这种洞报成"有人删过审计"
  ——那是假警报。时间口径（`auditDays`，默认 180 天）不变。
- **高风险操作双人复核**（1.30.50）：**默认关闭**。开启后，需要审批的动作提交时返回
  **`202 + approvalId`**（而不是 `201`）——**"已提交审批"与"已下发"是两件事**，界面文案已区分。
  申请人**不能批准自己的单子**（硬规则）；审批单默认 30 分钟过期即失效。设计件
  `superpowers/specs/2026-10-07-high-risk-approval-design.md`。
- **危险参数在提交前列出理由**（1.30.51）；`sudo` 高危命令按**事后发现**上报，
  规则**认完整路径**（sudo 日志记的是 `/bin/rm` 而非 `rm`）。设计件
  `superpowers/specs/2026-10-07-high-risk-command-design.md`。
- **护栏组合风险会上报到平台**（1.30.54）：安全中心新增卡片。**`null`（旧 Agent 未上报）与
  `[]`（已检查、无风险）分开显示**——把"没上报"显示成"没有风险"会让人以为那台机器是安全的。
- **审计防篡改（1.30.55，可检测）**：审计记录带链式 HMAC，新增 `GET /api/v1/audit/verify`
  与审计页「完整性校验」按钮。**它是「防篡改（可检测）」，不是「不可篡改」**——见第四节。
- **`release.sh` 的 manifest 自校验不再"空转通过"**（出包脚本，不影响运行时）：此前只判断 `jq` 命令是否存在，
  而**存在不等于能用**（本机就有一个坏掉的 jq），于是校验静默空转却打印"通过"。现在以
  "真的解出结果"为准，全不可用时**明确警告"已跳过、跳过 ≠ 通过"**。

## 二、新增能力（按主题）

### 资产与配置

- **资产关系**：拓扑视图（ECharts 力导向，点节点换中心）、**全库关系视图**（聚合看形态、筛选看连法）、
  `runs_on` 的宿主误判修复、`depends_on` 有了自动来源（副本 → 主库，主从切换会清掉过期边）、
  K8s **service → pod** 与 **中间件实例 → 集群**的自动归属边。
- **配置项模型页**：类型模型可读可写，巡检的字段范围收敛到一处；**自定义类型明确不做**。
- **资产批量维护与清单导出 CSV**；**变更历史与审计按请求 id 强关联**（双向入口：
  审计 → 本次改动的字段、变更 → 对应的审计记录）。

### 容器与集中日志

- **Pod 日志进集中日志检索**：Agent 侧按 `paths` 通配符采集、从文件路径解析容器身份随批次上报；
  服务端落身份并联动 Pod 资产；`pods=<命名空间>|<Pod>` 过滤在**两个后端语义一致**。
  修复了 **CRI 框架未剥离**（时间改用行内时间戳）。
- **日志后端可切换**：自研落盘 / 外部 VictoriaLogs（ADR-0002），保留策略页区分两者；
  新增 `deploy/install-logs.sh` 离线安装；修复按 JSON 解析时序库 `/flags` 的既有缺陷。
- **日志结构化解析与字段检索**（注意：字段检索仍是**有界扫描**，不是索引）。
- 容器页 → 集中日志检索的入口（按容器身份收窄）。

### 告警与报告

- **告警 ↔ 资产 ↔ 变更的关联闭环**：告警影响面、日志↔资产标签联动、**由日志创建告警规则**。
- **报告与巡检周期化**：报告按周期生成；**配置巡检**支持周期调度（范围只能由服务端按身份折算，
  手动"立即执行"额外按**点击者**范围收窄，保存者被删后不执行并写明原因）。

### 权限与审计

- **资源范围**：业务标签维度（见上）；**权限审计域**内的提权路径收口。
- **审计入库**：可按人 / 时间 / 路径 / 分类过滤并分页，不再被 2000 条截断；**合规矩阵导出 CSV**。
- **审计防篡改（可检测）**：链式 HMAC + 裁剪归因 + 日志锚点 + 校验接口（见第四节）。

### 下行操作与护栏

- **统一下行操作通道**：动作目录 + 任务状态机（`queued→delivered→running→succeeded/failed/expired`）
  + 能力协商 + 超时回收；**批量下发 / 整批取消 / 记录删除**；操作任务入库（不再受内存条数限制）。
- **四道护栏**：① 本机 `guards.ops`（默认只读；写动作需 `write:true` **且** 单元在 `units` 清单）；
  ② 能力协商（只下发本机声明放行的动作）；③ `ops:read` / `ops:exec` 权限点 + 参数校验 + 审计；
  ④ 默认只读。**护栏按"同意的性质"分设**：容器查询、文件分发各有独立开关。
- **双人复核**（1.30.50）、**危险参数判定**与**高危命令事后发现**（1.30.51）、
  **护栏组合风险上报**（1.30.54）。
- **补传排空预算动态化**（1.30.49，Agent）：断网积压恢复后**一轮排空**，并带 413 自愈与可见性指标。

## 三、刻意不做（及理由）

这些**不是没做完，是不做**。列出来是为了避免"怎么还没有"的反复讨论。

| 不做的事 | 理由 |
|---|---|
| **任意命令 / 脚本执行** | 唯一会把"逐机白名单"彻底作废的能力：能跑 `/bin/sh -c` 之后，"允许重启哪些单元""允许写哪些目录"就不再是安全边界，**攻破中心即等价于全网 root RCE**。有新排障需求时**加一个参数化动作**，不开 shell |
| **Web 在线终端 / 容器 exec 终端** | 同上。且 §3.4 明确：**若将来要放开，前置条件是双人复核 + 不可篡改审计**——双人复核已落地，**审计只做到"可检测"，前置仍未补齐** |
| **通用定时任务**（cron 表达式 + 任务注册表） | 需要定时的用例只有三条（拨测/报告/巡检），且要先解决三个前置：系统身份与权限、错过窗口语义（已有三套且互不相容）、多实例无锁 |
| **同一序列的降采样** | 会主动丢弃真实样本、改变曲线语义；且 spool 层没有序列维度 |
| **中间件 `exposes` 的自动来源** | 端口归并存在歧义（多个实例共用一个端口时无法判断暴露方）——**宁缺勿错** |
| **工作负载原始 YAML** | 只做白名单投影：原始 YAML 里可能带凭据、镜像仓库口令等，且体积不可控 |
| **自定义资产类型** | 类型清单收成一处、内置类型每次启动对齐标题；开放自定义会把范围/巡检/差异三处口径同时复杂化 |

## 四、风险后置（及前置条件）

| 后置项 | 前置条件现状 |
|---|---|
| **容器 exec 终端**（P2 / L） | 双人复核 **已落地**（1.30.50）；**不可篡改审计未补齐**——见下 |
| **镜像 / 配置安全扫描**（P3 / M） | 形态清楚（接 trivy），优先级最低 |
| **Server 高可用（A1）** | **暂缓** |
| **Agent 主备** | 依赖 A1；且要解决重复上报判重与脑裂 |

**关于"不可篡改审计"**：1.30.55 落地的是**链式 HMAC（可检测）**，不是"不可删除"。
**必须如实说清它防不住什么**：拿到该机 root 的人**能改库 + 能读密钥 + 能清日志**，本机制**防不住他**。
它防的是"只攻破应用/数据库这一层"：库被复制走改一份、SQL 改一行、删掉中间几行——
这些在 1.30.55 之前**一个都看不出来**。因此**"放开任意执行"的前置条件依然只满足了一半**，
这条不要被误读成"可以开始做 exec 了"。

## 五、运维动作（本次必须做的两件）

### 1. 备份审计链密钥文件

`/etc/monitor-server/audit.key`（**0600、root**，首次启动自动生成）是"没有它就无法伪造审计"的那把钥匙。
**它必须纳入备份**。**密钥丢失 = 历史不可验**：所有已写入的审计行都无法再校验。
（校验接口会区分"某条被改"与"换了密钥"，正是为了不把后者误报成安全事故——
所以报告里会带**密钥指纹**，换了密钥时你会看到它变了。）

**不要把密钥放进 `server.yaml`**，也不要通过任何接口取它（接口只返回指纹）。

### 2. 把日志锚点送往异地（要真正防住 root，只有这一步）

服务每 5 分钟（并在启动时立即）向服务日志写一行链头锚点：

```
audit chain head seq=<n> hash=<h> keyFingerprint=<fp>
```

**库内的链无法证明"尾部没被删"**——尾部没有后继来指认它；清空整张表更是完全不可检测。
锚点是**唯一**的库外依据，而它现在只落在本机 journald 上：**拿到 root 的人能连日志一起清**。
**要真正防住这一档，需要把服务日志（或至少这一行）投递到异地**（异地 syslog / 对象存储的对象锁等）。
**代码只负责把锚点吐出来，异地投递是运维侧的事**——这是整条防线上唯一由运维补齐的环节。

建议：把这一行单独抓出来（`grep 'audit chain head'`）送往异地；出现争议时用它和库里的链头比对。

## 六、测试与验证

- 后端 `go test ./...` 全绿、`go vet ./...` 干净；前端 `npm test` 26 文件 / 158 项通过、`npm run build` 成功。
- 近期能力均有**实机核对脚本**（在 `dist/` 下，不进版本库），各自带决定性判据与如实划线的未覆盖项：
  `inspect-sched-e2e.py`（38 项）、`ci-model-e2e.py`（35 项）、`spool-drain-e2e.py`（6 项）、
  `guardrisk-e2e.py`（13 项）、`audit-tamper-e2e.py`（14 项）。
- **已知的一处真实缺口（如实记录）**：`audit-tamper-e2e.py` 的**早先版本**在收尾时用
  "整表删除 + 按备份重插"做还原，抹掉了核对期间服务端新写的 3 行真实审计（seq 7..9）。
  后果是 dev-server 的审计链上留下一处**永久缺口**，`/api/v1/audit/verify` 会一直如实报
  `unattributable-gap`。**没有把它伪造成裁剪记录**——那才是作假；它被报出来恰恰说明机制在正常工作。
  脚本已改为**只补缺失行、绝不删除**。
- **未覆盖边界**（不得视为通过）：审计防篡改的"裁剪不算篡改"在真机上打不中（链上记录都是当天的，
  而保留窗口最小单位是"天"），只有用例覆盖；场景 D 的真实对抗（攻击者清库但不清日志）；
  场景 E（root，**不声称能防**）；多实例；导出 CSV 的第三方离线核对。

## 七、升级顺序

1. **先升 Server**（Web 端「系统升级」上传 upgrade 包，或脚本方式）。
2. Web 静态资源随 Server 升级包一并替换，无需单独操作。
3. **再升 Agent**（本版 Agent 侧有采集改动；升级后需重启 Agent）。
4. 升级后建议核对：
   - 登录一次 → 审计页点「完整性校验」→ 应看到**覆盖区间与条数**（不是只有一句"通过"）；
   - 安全中心「护栏组合风险」卡：**有风险或有节点未上报才出现**；
   - 若启用双人复核：提交一个写类动作，确认返回的是"**已提交审批**"而不是"已下发"。

## 八、未包含（后续跟进）

- **审计锚点的异地投递**（见第五节第 2 条）——需要运维侧接入。
- **不可篡改（不可删除）**：需要只追加的外部存储，属另一个量级的工程。
- 容器 exec 终端、镜像扫描、Server 高可用、Agent 主备（见第四节）。
- 审计 `auditDays` 的最小单位是"天"，无法配置到更细——这直接导致"裁剪不算篡改"在真机上难以验证。
- 审计防篡改的**多实例**约束：链要求单写者，当前是单实例 + 单库单连接；多实例下链会断。
